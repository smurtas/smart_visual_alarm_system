\section{Introduction}

The Internet of Things (IoT) enables physical devices to sense their
environment, process information, communicate with other devices and
services, and trigger actions according to the observed conditions.
An IoT system can therefore combine sensing, computation, communication,
and application-level services to transform observations of the physical
world into useful information and actions.

Visual monitoring represents a particularly challenging IoT application.
Compared with conventional sensors that produce relatively small amounts
of data, cameras continuously generate images containing a much larger
amount of information. A simple solution would be to transmit the acquired
images to a local server or cloud infrastructure and perform the required
computer vision processing remotely. However, this approach increases
network traffic, requires an external processing infrastructure, and
transmits visual information even when the observed scene does not contain
any relevant event.

An alternative approach is to move part of the computation closer to the
source of the data. In an edge computing architecture, information can be
processed locally before being transmitted to other components of the IoT
system. When machine learning inference is executed directly on
resource-constrained microcontrollers, this approach leads to Tiny Machine
Learning (TinyML).

TinyML combines machine learning with embedded computing under strict
constraints in terms of memory, storage, computational capability, latency,
and energy consumption. Consequently, developing a TinyML application
requires considering not only the predictive performance of a machine
learning model, but also whether the model can be efficiently executed on
the target embedded platform.

This paradigm is particularly suitable for an intelligent visual monitoring
system: rather than using the camera as a passive sensor that continuously
transmits images for remote analysis, the embedded device can locally
interpret the acquired visual information and communicate only when a
relevant event is detected.

This concept represents the starting point of the \emph{Smart visual alarm
system} developed in this project.

\section{System Overview}

\subsection{Use Case and Target Scenario}

The target scenario of this project is the monitoring of a mountain house environment. In this context, people and animals may pass near the entrance or in the surrounding outdoor area, also during evening or night hours. The objective is to develop a smart visual alarm system able to detect relevant visual events and notify the user remotely.

Unlike a generic indoor people detection system, this project focuses on a more specific real-world scenario. The monitored area is expected to contain different types of situations: an empty scene, the presence of a person, or the presence of a generic animal. The goal is not to recognize the animal species, since this would require a larger and more complex dataset, but to distinguish between the main classes that are relevant for the alarm system.

The camera is positioned near the entrance of the house, with a clear view
of the monitored outdoor area. The camera observes the scene through a
window protected by metal bars, which are therefore permanently visible
in the foreground of the acquired images. These elements can partially
occlude people or animals and make visual classification more challenging,
especially when a subject is located behind or close to the bars.

The installation environment also includes an automatic light that is
activated by motion. This provides additional illumination under low-light
conditions without requiring an infrared camera, although night-time visual
classification is not considered a separate machine learning task in this
project.

The proposed use case is therefore based on three target classes:
\begin{itemize}
    \item \textbf{Empty}: no relevant subject is visible in the monitored area;
    \item \textbf{Person}: at least one person is visible in the scene;
    \item \textbf{Animal}: at least one animal is visible in the scene,
without distinguishing its species.
\end{itemize}

When the system identifies a \textit{person} or an \textit{animal}, the
prediction confidence is evaluated before generating an alarm. In the final
implementation, an application-level confidence threshold of 0.85 (85\%) is used:
only detections with a confidence equal to or greater than this threshold
are propagated through the IoT notification pipeline. Lower-confidence
predictions remain visible in the device logs for diagnostic purposes but
do not generate an external alert.

When the alert condition is satisfied, the captured image is transferred
from the ESP32-S3-EYE to the Raspberry Pi through HTTP, while the detection
event is published through MQTT. The event is subsequently processed using
Node-RED and a Telegram notification containing the captured image is sent
to the user. The resulting use case therefore combines local TinyML
inference with event-driven IoT communication, allowing both the visual
classification behaviour and the complete notification pipeline to be
evaluated in a real monitoring environment.

\subsection{General System Architecture}
\label{subsec:general-architecture}

The overall architecture of the Smart Visual Alarm System is shown in
Figure~\ref{fig:system_architecture}. The system is organized around an
ESP32-S3-EYE edge node, a Raspberry Pi gateway, an MQTT communication layer,
Node-RED, and a Telegram notification service.

The ESP32-S3-EYE performs image acquisition, preprocessing, TinyML inference,
and the application-level alert decision locally. When a relevant event is
detected, the captured image is transferred to the Raspberry Pi through HTTP,
while the detection event is published through MQTT. The Raspberry Pi then
handles the downstream IoT integration, and Node-RED processes the event flow
that ultimately triggers the Telegram notification.

In this architecture, image classification is performed on the ESP32-S3-EYE, 
while communication and notification tasks are handled by the Raspberry Pi.

\subsection{Hardware Components}
\label{subsec:hardware-components}

The hardware architecture is based on two main devices: the ESP32-S3-EYE
and a Raspberry Pi. The two platforms have complementary roles within the
system.

The ESP32-S3-EYE acts as the intelligent sensing node. It acquires images
from the monitored environment and performs the complete local inference
pipeline, including image preprocessing, execution of the TinyML model, and
evaluation of the resulting prediction. Its role is therefore not limited
to image acquisition: the device is responsible for deciding whether the
observed scene contains a relevant event before any alert is propagated
through the network.

The Raspberry Pi acts as the local gateway and integration platform. It
provides the services required to receive images from the ESP32-S3-EYE,
manage MQTT-based event communication, execute the Node-RED workflow, and
support the final Telegram notification process. Compared with the
microcontroller, the Raspberry Pi offers substantially greater computing,
storage, and networking capabilities, making it suitable for the
communication and application-level components that do not need to execute
directly on the embedded sensing node.

This division of responsibilities reflects the edge-oriented design of the
system: latency-sensitive visual inference is performed directly on the
ESP32-S3-EYE, while higher-level communication and integration tasks are
delegated to the Raspberry Pi.

\subsection{Software Components}
\label{subsec:software-components}

The software architecture of the Smart visual alarm system combines
embedded development, machine learning, communication protocols, and
flow-based IoT integration. Different software components are used at
different stages of the project, from neural network development and
deployment to the execution of the final notification pipeline.

On the embedded side, the ESP32-S3-EYE firmware is developed using
ESP-IDF. The firmware integrates camera acquisition, image preprocessing,
execution of the deployed TinyML model, application-level decision logic,
Wi-Fi connectivity, HTTP communication, and MQTT event publication.

The machine learning development pipeline is implemented in Python using
PyTorch. It includes dataset loading and preprocessing, model definition,
training, validation, and evaluation. After training, the selected model is
converted and quantized for deployment on the ESP32-S3-EYE, where inference
is performed locally using the Espressif embedded machine learning
infrastructure.

On the Raspberry Pi, the software stack provides the services required to
receive images and process alarm events. MQTT is used for lightweight
event communication, while HTTP is used for image transfer. Node-RED
orchestrates the downstream event flow and integrates the detection events
with Telegram, which provides the final remote notification to the user.

The resulting software stack therefore connects two distinct domains:
the machine learning pipeline used to develop and optimize the classifier,
and the IoT runtime infrastructure used to transform an on-device inference
result into a remote notification.

\section{Dataset Acquisition and Preparation}
\label{sec:dataset}

\subsection{Data Collection}
\label{subsec:data-collection}

A dedicated dataset was created for the development of the visual
classification model. The images were collected directly from the
ESP32-S3-EYE installed in the target monitoring environment, rather than
relying exclusively on an existing public dataset. This approach was chosen
to make the training data representative of the visual conditions that the
deployed system would encounter.

The camera was configured to acquire images of the entrance and surrounding
outdoor area of the mountain house. As a consequence, the collected images
share the same viewpoint and contain environmental characteristics that are
specific to the final deployment scenario, including the background,
illumination variations, subject distance, and the metal bars located in
front of the camera. These characteristics are particularly relevant because
they directly affect the visual information available to the classifier.

During the initial acquisition phase, images were periodically captured by
the ESP32-S3-EYE and transferred through the local network to the Raspberry
Pi, where they were stored for subsequent dataset preparation. At this stage,
the objective was to collect raw observations of the real environment before
performing manual classification into the three target classes:
\texttt{empty}, \texttt{person}, and \texttt{animal}.

Collecting the dataset in the actual deployment environment improves its
relevance to the target application, but also introduces an important
limitation: naturally occurring events are not equally frequent. Empty
scenes were significantly more common than images containing people and,
especially, animals. This class imbalance became one of the main challenges
of the dataset preparation process and required additional processing steps,
as discussed in the following subsections.
\subsection{Manual Labelling}
\label{subsec:manual-labelling}

After the acquisition phase, the collected images had to be manually
inspected and assigned to the correct target class. A dedicated Python
script, \texttt{label\_dataset.py}, was developed to support this process
and to create a consistently labelled dataset for model training.

The script displays the collected images sequentially and allows the user
to assign each image to one of the three classes: \texttt{empty},
\texttt{person}, or \texttt{animal}. Images that are corrupted, ambiguous,
or otherwise unsuitable for training can instead be assigned to a separate
\texttt{rejected} category. According to the selected label, the image is
automatically moved to the corresponding class directory.

Manual inspection was particularly important in this project because the
images were collected automatically from a real outdoor environment.
Consequently, not every acquired frame necessarily provided a clear and
useful training example. The labelling stage therefore served both to
associate each image with its ground-truth class and to perform an initial
quality-control step before training the neural networks.

The dataset directory structure was subsequently reorganized during the
development of the project. Therefore, the intermediate directory structure
used during the initial acquisition and labelling phases does not correspond
exactly to the final organization of the repository.

\subsection{Dataset Challenges and Class Imbalance}
\label{subsec:dataset-imbalance}

The acquisition of images directly from the real deployment environment
introduced a significant class imbalance. Since the camera continuously
observed the entrance area, most of the automatically collected frames
represented the \texttt{empty} class. Images containing a person were less
frequent, while animal occurrences were particularly rare.

This imbalance is a direct consequence of the target scenario. An empty
entrance represents the normal operating condition of the system, whereas
the presence of a person or an animal corresponds to a comparatively
infrequent event. Therefore, simply using all the acquired images would
have produced a dataset strongly dominated by the \texttt{empty} class.

Such a distribution would be problematic for model training. A classifier
trained on a highly imbalanced dataset could obtain apparently high overall
accuracy by favouring the majority class, while performing poorly on the
classes that are actually the most relevant for the alarm system.

For this reason, the complete collection of raw images was not used directly
for training. Instead, the number of samples selected from the different
classes was controlled during dataset preparation. The \texttt{animal}
class required particular attention because naturally acquired examples
were much more difficult to obtain in the monitored environment.

\subsection{Dataset Enrichment and Data Augmentation}
\label{subsec:data-augmentation}

The most significant limitation of the collected dataset concerned the
\texttt{animal} class. While empty scenes were naturally abundant and
person images could be deliberately collected in the monitored area, only
two usable animal images were obtained during the original acquisition
phase.

Since this amount of data was insufficient for training a three-class
classifier, the animal class was enriched with additional examples in order
to increase its visual variability. The resulting dataset contained 120
animal images. This enrichment was necessary to make the animal class
usable in the experimental comparison, although the very limited number
of original real-world animal observations remains an important limitation
of the dataset.

A second and distinct strategy was applied during model training through
on-the-fly data augmentation. Training images were first resized to
$48 \times 48$ pixels. Random horizontal flipping was applied with a
probability of 0.5, together with rotations of up to $\pm 3^\circ$.
Random affine transformations introduced translations of up to 8\% of the
image dimensions and scaling between 0.90 and 1.10.

Photometric variability was introduced using colour jitter, with variations
in brightness, contrast, saturation, and hue. In particular, the configured
factors were 0.35 for brightness, 0.25 for contrast, 0.10 for saturation,
and 0.02 for hue. Gaussian blur was additionally applied with a probability
of 0.15.

These transformations were generated dynamically during training rather
than stored as additional copies in the dataset. Consequently, the same
source image could appear with different visual characteristics across
training epochs.

After augmentation, images were converted to tensors and normalized using
the ImageNet mean and standard deviation. The randomized augmentation
pipeline was applied exclusively to the training set. Validation and test
images were only resized to $48 \times 48$, converted to tensors, and
normalized using the same parameters.


\subsection{Dataset Split}
\label{subsec:dataset-split}

After the dataset preparation process, the selected images were divided
into independent training, validation, and test subsets using a stratified
70\%--15\%--15\% split. A fixed random seed of 42 was used to make the
selection and splitting procedure reproducible.

To reduce the effect of the large number of available empty images, a
maximum of 140 images per class was considered during dataset preparation.
Both the \texttt{empty} and \texttt{person} classes reached this limit,
whereas 120 images were available for the \texttt{animal} class. The final
dataset therefore contained 400 images.

\section{Machine Learning Models}
\label{sec:models}

\subsection{Model Selection Strategy}
\label{subsec:model-selection}

The machine learning component of the Smart Visual Alarm System was
developed as a three-class image classification problem, with
\texttt{animal}, \texttt{empty}, and \texttt{person} as the target classes.
However, predictive performance alone was not sufficient to determine the
most suitable model for the final application. Since inference had to be
executed directly on the ESP32-S3-EYE, the computational and memory
requirements of the model also had to be considered.

For this reason, the project followed a comparative approach rather than
selecting a single neural network architecture from the beginning. Three
different models were investigated: a Multilayer Perceptron (MLP), used as
a simple baseline; TinyViT, representing a more advanced vision architecture;
and MCUNet, an architecture specifically designed for machine learning on
resource-constrained microcontrollers.

The MLP provides a useful reference point for evaluating whether more
specialized image-processing architectures provide a meaningful advantage.
Since it processes flattened image data through fully connected layers, it
does not explicitly exploit the spatial structure of the input image and
can require a relatively large number of parameters.

TinyViT was investigated as a more sophisticated alternative based on
modern vision architectures. Its inclusion makes it possible to evaluate
whether a more expressive model can provide improved classification
performance while considering the additional computational complexity
associated with deployment on a constrained embedded platform.

MCUNet was selected as the architecture most closely aligned with the
TinyML requirements of the project. Its design targets microcontroller
environments, where memory consumption, model size, and computational cost
are important constraints in addition to classification accuracy. This
makes it particularly relevant for deployment on the ESP32-S3-EYE.

The three architectures therefore represent different points in the design
space, from a simple baseline to increasingly specialized visual models.
They were trained and evaluated using the same dataset organization so that
their behaviour could be compared under consistent experimental conditions.
The final model selection was then based not only on predictive performance,
but also on the practical requirements of embedded deployment.

\subsection{MLP Baseline}
\label{subsec:mlp}

The first model tested in this project was a Multilayer Perceptron (MLP).
The purpose of this model was to provide a simple baseline that could be
used as a reference for the comparison with the other neural network
architectures.

Unlike convolutional neural networks, an MLP does not directly use the
spatial structure of an image. Each input image is therefore resized and
converted into a tensor, and the resulting pixel values are flattened into
a one-dimensional vector before being processed by the fully connected
layers of the network.

An initial version of the MLP was tested during the development of the
project. However, this model contained more than seven million parameters,
which was too large considering the target embedded platform. A second,
smaller version was therefore developed using $48 \times 48$ input images.
This significantly reduced the number of parameters while keeping the MLP
useful as a baseline classifier.

The final MLP architecture consists of fully connected layers followed by
non-linear activation functions. Dropout is also used during training to
reduce overfitting. The output layer contains three neurons, corresponding
to the three classes used in the project: \texttt{animal},
\texttt{empty}, and \texttt{person}.

The MLP was not expected to be the final model deployed on the
ESP32-S3-EYE. Its main purpose was to establish a simple reference model
and to show the limitations of using fully connected layers for image
classification, especially when model size and memory usage are important
constraints.

\subsection{TinyViT}
\label{subsec:tinyvit}

The second model considered in the project was TinyViT. The purpose of
testing this model was to compare the simple MLP baseline with a more
advanced architecture designed for computer vision tasks.

Vision Transformer models process images differently from traditional
convolutional neural networks. Instead of relying only on convolutional
operations, they use attention mechanisms to learn relationships between
different regions of an image. Standard Vision Transformers, however, can
be computationally expensive and are generally not suitable for small
microcontrollers.

TinyViT was designed to reduce this computational cost while keeping some
of the main advantages of transformer-based vision models. For this reason,
it was an interesting candidate for this project, where the model has to
classify images while also respecting the hardware limitations of the
ESP32-S3-EYE.

As for the other models, TinyViT was trained to classify the three target
classes: \texttt{animal}, \texttt{empty}, and \texttt{person}. The same
dataset split was used so that its results could later be compared with
those obtained with the MLP and MCUNet.

Although TinyViT offers a more advanced approach to image classification,
its suitability for this project also depends on its model size,
computational requirements, and the possibility of deploying it on the
target microcontroller. These aspects were therefore considered together
with its classification performance when comparing the three models.

\subsection{MCUNet}
\label{subsec:mcunet}

The third model evaluated in the project was MCUNet. This model was
particularly interesting because it is designed for machine learning
applications running on microcontrollers, where memory and computational
resources are limited.

Compared with the MLP and TinyViT, MCUNet is more closely related to the
final objective of the project: running the complete image classification
process directly on the ESP32-S3-EYE. For this reason, the architecture
needs to remain small enough for embedded deployment while still providing
good classification performance.

The implemented network is based on convolutional layers and inverted
residual blocks. These blocks allow the network to extract increasingly
complex visual features without requiring a very large number of
parameters. The number of channels increases through the network as the
spatial dimensions of the feature maps are progressively reduced.

At the end of the feature extraction stage, global average pooling is used
to reduce each feature map to a single value. The resulting features are
then passed to the final classification layer, which produces the scores
for the three classes: \texttt{animal}, \texttt{empty}, and
\texttt{person}. Dropout is also used before the final classification stage
to reduce overfitting.

MCUNet was trained using the same dataset organization used for the other
models. After the comparison between the three architectures, this model
was selected for the final embedded implementation. The trained network was
then quantized to INT8 and converted to a format that could be executed on
the ESP32-S3-EYE. The quantization and deployment process is described in
a later section.

\section{Training and Model Evaluation}
\label{sec:training-evaluation}

\subsection{Training Setup}
\label{subsec:training-setup}

The three models were trained using PyTorch. The same dataset organization
was used for all the experiments, with separate training, validation, and
test sets as described in the previous section.

All input images were resized to $48 \times 48$ pixels before being passed
to the models. During training, data augmentation was applied dynamically
to the training images, while validation and test images were only resized
and normalized. The images were processed in batches of 16 samples.

The training set was shuffled at the beginning of each epoch. The validation
set was used during the training process to check how well the model was
generalizing to images not used for parameter optimization. The test set,
instead, was kept separate and used only for the final evaluation.

During the experiments, the training and validation loss were monitored
across the epochs. Validation performance was also used to identify the
best model obtained during training and to avoid selecting a model only
according to its performance on the training data.

After training, each model was evaluated on the same test set. This made it
possible to compare the different architectures under the same conditions
and to evaluate both their classification performance and their suitability
for the final embedded application.

\subsection{Model Evaluation and Selection}
\label{subsec:model-evaluation}

After training, the three models were evaluated using the same test set.
Accuracy was used to measure the percentage of correctly classified images.
Precision, recall, and F1-score were also considered to analyse the
performance of the models on the individual classes. The confusion matrix
was used to identify which classes were more frequently confused.

The Macro F1-score was particularly useful because it gives the same
importance to each class when calculating the average performance. This is
relevant in this project because the final dataset is not perfectly balanced,
with 120 animal images and 140 images for each of the other two classes.

However, classification performance was not the only criterion used to
select the final model. The classifier had to run directly on the
ESP32-S3-EYE, so the number of parameters, model size, and computational
requirements were also important. A model with high accuracy but excessive
memory or computation requirements would not be suitable for the final
system.

The MLP was used as a baseline, while TinyViT and MCUNet were tested as
alternative architectures for image classification. The three models were
trained and tested using the same dataset organization, allowing their
results to be compared under the same conditions.

\section{TinyML Deployment on the ESP32-S3-EYE}
\label{sec:tinyml-deployment}

After the comparison of the three models, MCUNet was selected for the final
implementation on the ESP32-S3-EYE. The next step was therefore to convert
the trained PyTorch model into a format suitable for execution on the
microcontroller.

Running a neural network on a microcontroller introduces stronger resource
constraints than running the same model on a computer. In particular, the
available memory and computational power are limited. For this reason, the
trained MCUNet model was quantized from floating-point representation to
8-bit integers (INT8).

Post-training quantization was performed using a separate calibration
dataset containing 60 images, with 20 samples for each of the three classes.
The calibration images were used to determine the numerical ranges required
for INT8 quantization and were kept separate from the dataset used for
training and final model evaluation.

After quantization, the model was converted to the format required by the
Espressif embedded machine learning framework and integrated into the
ESP-IDF firmware. The final model is stored directly in the firmware and
inference is therefore performed locally on the ESP32-S3-EYE without
requiring a remote machine learning service.

During operation, the ESP32-S3-EYE captures an image from the camera and
preprocesses it according to the input requirements of the deployed model.
The processed image is passed to the INT8 MCUNet model, which produces a
prediction for the three classes: \texttt{animal}, \texttt{empty}, and
\texttt{person}, together with the corresponding confidence values.

The predicted class and confidence are then used by the application logic.
The \texttt{empty} class does not generate an alarm. For
\texttt{person} and \texttt{animal}, an alert is generated only when the
prediction confidence is equal to or greater than 0.85. Predictions below
this threshold are still printed in the device logs but are not sent to
the notification system.

In the final firmware, inference is executed approximately every two
seconds. At startup, the camera also captures and discards eight frames
before starting the inference loop. This warm-up phase allows the camera
to stabilize before images are used by the classifier.

Performing inference directly on the ESP32-S3-EYE is an important part of
the project. Images do not need to be continuously transmitted to another
device for classification. Instead, the microcontroller first analyses the
scene locally and starts the communication pipeline only when the detected
event satisfies the alert conditions.

\section{IoT Communication and Notification System}
\label{sec:iot-communication}

Once a relevant event is detected by the ESP32-S3-EYE, the result has to be
transmitted to the rest of the system. Two communication mechanisms are used
for this purpose: HTTP for transferring the captured image and MQTT for
publishing the detection event.

HTTP is used because the captured JPEG image has to be transferred as a
complete file to the Raspberry Pi. When the alert condition is satisfied,
the ESP32-S3-EYE sends the captured image to an HTTP service running on the
Raspberry Pi. The received image is then stored locally and can be used in
the final notification.

MQTT is used separately to communicate the detection event. The
ESP32-S3-EYE acts as an MQTT publisher and sends a message containing
information about the detected class and its confidence. The Raspberry Pi
hosts the MQTT infrastructure used by the system, while Node-RED receives
and processes the published events.

Using HTTP and MQTT for different purposes keeps the two types of
communication separate. HTTP handles the image data, while MQTT provides a
lightweight mechanism for sending the event generated by the classifier.
This also avoids including the complete image inside the MQTT message.

Node-RED is used on the Raspberry Pi to connect the detection event with the
notification service. When a new MQTT event is received, the flow processes
the message and prepares the information required for the notification.
Both \texttt{person} and \texttt{animal} detections can generate an alert,
provided that the confidence threshold has been satisfied on the
ESP32-S3-EYE. The image previously received through HTTP is then associated
with the corresponding event.

The final notification is sent through Telegram. It contains the image
captured when the detection occurred together with the detected class and
confidence. In this way, the user can immediately see whether a person or
an animal has been detected without directly accessing the Raspberry Pi or
the ESP32-S3-EYE.

The complete communication process is therefore activated only after the
local inference and alert decision. Under normal conditions, when the scene
is classified as \texttt{empty} or when the confidence of a relevant class
is below the configured threshold, no image or alarm event is sent. This
reduces unnecessary network communication and keeps the classification task
on the edge device.

\section{System Integration and Testing}
\label{sec:system-testing}

After the individual components were developed, the complete system was
tested by connecting the ESP32-S3-EYE, the Raspberry Pi, the MQTT
communication, Node-RED, and Telegram.

The ESP32-S3-EYE was installed in the target environment and used to
continuously acquire images from the monitored area. Every two seconds, a
new frame was processed and classified locally by the deployed MCUNet
model. The predicted class and confidence were printed in the device logs,
which made it possible to check the behaviour of the classifier during
real operation.

The complete notification pipeline was tested using both
\texttt{person} and \texttt{animal} detections. When one of these classes
was detected with a confidence of at least 0.85, the ESP32-S3-EYE sent the
captured image to the Raspberry Pi through HTTP and published the detection
event through MQTT. Node-RED processed the event and generated the Telegram
notification containing the image, detected class, and confidence.

Detections below the configured threshold were also useful during testing.
They remained visible in the ESP32-S3-EYE logs but did not activate the
communication and notification pipeline. This allowed the confidence
threshold to act as an additional filter between the classifier output and
the actual alarm.

The tests also showed some limitations of the classifier in the real
environment. In some situations, objects or parts of the background could
produce an incorrect prediction, especially when the visual characteristics
of the scene were similar to examples seen during training. This behaviour
is important because the dataset was relatively small and the camera always
observed the same environment.

Despite these limitations, the integration tests confirmed that the complete
IoT pipeline could operate from end to end: an image was acquired and
classified on the ESP32-S3-EYE, the alert condition was evaluated locally,
the image and event were transmitted to the Raspberry Pi, and the final
notification was delivered through Telegram.
